# 수정 합의와 최종 검토

기존 답변의 부분 수정, 반복 피드백, 최종 제출 가능 여부를 검토할 때 사용한다. 사용자가 같은 설명을 반복하지 않도록 합의한 내용을 보존하고, 수정 결과를 반환하기 전에 관련 문맥까지 검사한다.

## 1. 현재 요청과 합의를 확인한다

현재 대화와 최신 자료에서 다음을 확인한다. 별도 상태 파일이나 사용자에게 보여줄 긴 계획표를 매번 만들 필요는 없다.

- 작업 대상: 문항, 문단, 문장 또는 실제 첨부 파일.
- 수정 종류: 소재 선택, 구조 변경, 문체 조정, 사실 확인, 읽기 전용 평가.
- 보존할 내용: 사용자가 좋다고 한 문단, 선택한 소재와 메시지, 분량과 말투.
- 제외할 내용: 쓰지 않기로 한 프로젝트, 불필요한 기술명, 반복하지 않기로 한 다짐.
- 최신 확인: 사용자가 정정한 역할·수치·기간과 아직 해소되지 않은 충돌.

이미 받은 설명이나 파일을 먼저 확인한다. 질문이 필요하면 답변의 진위·방향에 실제 영향을 주는 미확인 내용만 묻는다. 과거 요약의 누락을 현재 사용자의 명시적인 확인보다 우선하지 않는다.

## 2. 요청한 범위 안에서 수정한다

- `이 문단은 좋다`고 했으면 다른 부분을 고치면서 임의로 다시 쓰지 않는다.
- `말투만 다듬어 달라`면 소재·주장·성과·동기를 추가하거나 바꾸지 않는다.
- 구조 변경을 요청하면 먼저 문단별 역할과 정보의 순서를 정한다. 단어만 바꾸며 같은 문제를 반복하지 않는다.
- 수정한 부분은 인접 문장과 문단 전체까지 다시 읽는다. 부분 수정이 전체 맥락과 충돌하면 필요한 연결만 최소한으로 조정한다.
- 보존하기로 한 내용에서 사실·문항 조건의 충돌이 발견되면 구체적인 이유를 알리고 수정 필요를 제시한다. 합의를 보존한다는 이유로 오류를 남기지는 않는다.

사용자의 피드백을 그대로 동의만 하고 확대하지 않는다. 예를 들어 특정 환경의 모든 지연이 안전에 직결된다는 주장이라면 기능·조건에 따라 성립하는지 검토하고 적절한 강도로 고친다.

## 3. 반복해서 실패하기 쉬운 요청

아래 예시는 편집 판단을 설명하기 위한 것이다. 예시의 경험을 다른 지원자의 사실로 복사하지 않는다.

| 요청 또는 초안 | 피할 응답 | 필요한 판단과 수정 |
|---|---|---|
| `직무에서 필요한 역량을 써 달라` | `요청을 실행하는 역량이 중요합니다`처럼 과업을 바꿔 말한다. | 무엇을 이해·설계·분석할 수 있어야 하는지 정의하고 본문의 실제 행동이 이를 보여주는지 본다. |
| `계산 방식을 바꿔 메모리를 줄였다` | 기술명과 성과만 추가하거나 전체 학습 메모리 절감으로 확대한다. | 제공된 사실에서 문제, 분석, 변경 방식, 해당 연산의 측정 범위를 살린다. |
| `자연스럽게 연결되는 서비스의 예시로 일정·길안내와 음악·공조를 넣어 달라` | 모든 기능을 반드시 순서대로 실행하는 이야기로 만든다. | 전체 목표를 먼저 두고, 연속 실행되는 예시와 나란한 개인화 예시를 구분한다. |
| `작게 시작하는 태도를 운동과 어학 경험으로 설명해 달라` | 직무와 무관하다고 삭제하거나 업무 지연까지 극복했다고 쓴다. | 생활 속 반복된 실천과 현재의 태도로 설명하고 개선 범위를 확대하지 않는다. |
| `최종본을 냉정하게 평가해 달라` | 우선 괜찮다고 말하고 재질문마다 오타·논리 문제를 하나씩 추가한다. | 최신 파일을 전체 검토하고 발견한 필수 수정과 선택적 개선을 모아서 제시한다. |

## 4. 최종 검토는 최신 실제 본문으로 한다

최종본이 첨부되면 이전 채팅의 초안이나 문서에 적힌 글자 수를 그대로 믿지 않고 실제 본문을 읽는다. 파일을 읽지 못했다면 그 한계를 밝히고 읽었다고 하지 않는다. 내용만 검토했다면 시각적 레이아웃까지 검증했다고 하지 않는다.

다음 관점으로 전체를 점검한 뒤 발견 사항을 모아 답한다.

1. 문항: 원문과 하위 요구에 모두 답했는가. 직무 내용과 필요한 역량을 구분했는가.
2. 정보와 논리: 필요한 배경이 있고, 주장과 경험이 연결되며, 인과·예시·병렬 관계가 성립하는가.
3. 전체 답변: 소재·수치·결론의 불필요한 반복이나 다른 문항과의 충돌이 없는가.
4. 사실과 범위: 본인 역할, 팀 성과, 지표의 대상·기준선·측정 조건을 보존했는가.
5. 문장과 형식: 문법, 오타, 고유명사, 편집 흔적, 블라인드 지침과 글자 수를 확인했는가.

글자 수는 질문·제목·검토 메모와 답변 본문을 구분해 계산하고, 공백·줄바꿈 포함 여부를 명시한다. 실제 입력창을 확인하지 않았다면 로컬 계산 결과를 입력창 검증이라고 부르지 않는다.

## 5. 수정의 중요도와 제출 판단을 구분한다

| 구분 | 판단과 출력 |
|---|---|
| 제출 전 수정 필요 | 문항 누락, 사실 충돌·과장, 의미가 달라지는 지표, 논리 단절, 문법·오타, 형식·분량 위반. 위치와 이유, 필요한 경우 바로 교체할 문장을 제시한다. |
| 선택적인 개선 | 의미가 같은 표현·순서 선택, 현재도 이해되는 문장의 간결화, 문단 분리 등. 제출을 막는 조건으로 만들지 않는다. |
| 현재 글의 한계 | 회사 선택 이유가 약하거나 직접 경험이 부족한 등 경쟁력의 한계. 사실을 꾸며 메울 수 없음을 밝히고 글의 판단과 실제 선발 결과를 구분한다. |

다음처럼 검토 범위에 맞춰 결론을 낸다.

- 필수 문제를 확인하지 못했다면 검토 범위를 밝히고 제출 가능한 수준인지 평가한다. 합격 가능성이나 지원자 전체 중 순위를 근거 없이 수치화하지 않는다.
- 수정이 필요하면 발견한 문제를 한 번에 모으고, 해결 후 제출할 수 있는지 말한다. 수정안을 제시한 뒤 불필요하게 전체 재작성을 요구하지 않는다.
- 원시 실험 기록 없이 이력서와 사용자 설명만 대조했다면 해당 범위까지만 확인했다고 말한다. 실제 검토하지 않은 근거를 확인한 것처럼 쓰지 않는다.
- 재질문에서 실제 오류를 발견하면 숨기지 않고 정정한다. 처음부터 있던 문제라면 이전 검토의 누락임을 인정하고 관련 부분도 재검사한다.
- 새 사실·수정·논리 문제가 없으면 취향에 따른 변경을 필수로 승격하거나 이미 합의한 방향을 반복해서 뒤집지 않는다.

최종 평가는 새 초안 작성과 구분한다. 사용자에게 승인받지 않은 파일 변경이나 지원서 제출을 수행하지 않는다.
