## 1. 적용 우선순위

다음 순서로 적용한다.

1. 현재 공고의 문항·평가표·제출 형식·글자 수·블라인드 지침
2. 사용자가 제공한 사실과 원기록
3. 공식 지침과 여러 직무 사례가 함께 지지하는 원칙
4. 합격 사례에서 자주 관찰된 구조와 표현
5. 문체와 표현 선호

합격 사례에 존재한다는 사실만으로 좋은 패턴이나 합격 원인이라고 보지 않는다. 현재 공고가 목록, 키워드, 우선순위, 지정 소제목을 요구하면 일반적인 서사 구조보다 그 형식을 먼저 따른다.

## 2. 제출 하드게이트

초안 전에 다음을 한곳에 기록한다.

| 항목 | 확인할 내용 |
|---|---|
| 문항 | 원문, 하위 질문, 평가 동사, 필수·선택 여부 |
| 형식 | 항목 순서, 목록·키워드·소제목 지시, 첨부 방식 |
| 분량 | 최소·최대 글자 수, 공백·줄바꿈 포함 여부, 입력창 기준 |
| 지원 대상 | 회사·조직·직무·고용 형태 |
| 블라인드 | 학교·출신지·가족·성별 등 현재 기관이 금지한 정보 |
| 사실성 | 허위 기재 금지, 증빙 가능 범위, 대외비·개인정보 제외 |

문항이 여러 요구를 한 문장에 담고 있으면 각각을 체크 항목으로 분리한다. 일반적인 블라인드 관행을 모든 기업에 일률 적용하지 말고 현재 공고의 지침을 확인한다.

## 3. 사실과 주체 관리

경험마다 다음을 분리해 기록한다.

| 항목 | 확인할 내용 |
|---|---|
| 상황과 제약 | 당시 실제 조건, 기간, 자원, 문제의 범위 |
| 본인의 판단 | 직접 관찰·가설 설정·비교·선택한 내용 |
| 본인의 행동 | 직접 분석·설계·구현·조정·검증한 일 |
| 타인의 행동 | 팀원·현업·멘토가 판단하거나 수행한 일 |
| 팀의 결과 | 개인에게 단독 귀속하면 안 되는 성과 |
| 수치 | 기준선, 결과, 적용 대상, 측정 조건 |
| 비수치 증거 | 채택·배포·재사용·승인·피드백·산출물 등 |
| 확인 상태 | 원기록 확인, 사용자 진술, 추정, 충돌 |

각 행동 문장 앞에 `내가`를 붙여도 사실인지 점검한다. 타인의 판단과 팀 성과를 개인 성과로 바꾸지 않되, 본인의 실제 기여도 모호한 주어로 축소하지 않는다.

팀 보고서·발표자료·코드·결과 파일은 프로젝트의 행동과 결과를 증명할 수 있지만 개인의 역할을 자동으로 증명하지는 않는다. 개인 주어를 쓰려면 지원자가 그 행동을 맡았다는 명시적인 사용자 진술, 역할 기록, 커밋·작성자 정보 등 별도 근거가 있어야 한다. 근거가 없으면 팀 또는 프로젝트 주어로 낮추거나 해당 행동을 뺀다.

다음과 같은 역할 확장은 금지한다.

- `팀원`을 근거 없이 `조장·팀장`으로 바꾼다.
- 팀이 만든 산출물을 본인이 단독 구현한 것으로 바꾼다.
- 분석에서 제안이 도출됐다는 사실을 본인이 현직자·고객에게 직접 전달한 것으로 바꾼다.
- 문서에 적힌 원인 가설을 본인이 확정 진단한 결과로 바꾼다.

기록이 충돌하면 원기록이나 사용자의 명시적인 현재 확인으로 해소한다. 출처 우선순위는 `원본 결과물·증빙 → 사용자의 현재 확인 → 파생 요약 → 기존 지원서 초안`이다. 다만 상위 출처를 실제로 확인하지 않았다면 우선순위만으로 값을 추정하지 않는다.

확인할 수 없으면 충돌하는 수치·명칭·성과를 제출용 본문에서 모두 빼거나 공통으로 성립하는 보수적 표현을 사용한다. 기존 초안의 값을 유지하거나 여러 값 중 더 그럴듯한 하나를 임의로 선택하지 않는다. 확인 필요 목록에 충돌을 적었다는 사실은 그 값을 본문에 사용할 수 있다는 뜻이 아니다.

## 4. 경험과 직무의 근접도 비교

가장 화려한 경험보다 목표 직무의 실제 과업과 가까운 경험을 우선한다.

| 비교축 | 목표 직무에서 볼 것 | 경험에서 볼 것 |
|---|---|---|
| 해결 문제 | 어떤 문제를 해결하는가 | 비슷한 종류의 문제를 다뤘는가 |
| 정보·도구 | 데이터·설비·고객정보·규정·기술 | 같은 종류의 정보나 도구를 다뤘는가 |
| 이해관계자 | 고객·현장·개발·공공 이해관계자 | 비슷한 상대와 조정하거나 협업했는가 |
| 성과 기준 | 품질·시간·매출·정확성·안전·사용성 | 비슷한 기준으로 결과를 검증했는가 |

후보 경험은 다음 순서로 비교한다.

1. 문항에 직접 답하는가
2. 직무와 네 비교축이 얼마나 겹치는가
3. 본인의 판단과 행동이 선명한가
4. 결과나 근거를 확인할 수 있는가
5. 다른 지원자와 구분되는가
6. 짧은 설명으로 이해할 수 있는가
7. 다른 문항과 불필요하게 중복되지 않는가

기본은 주 경험 1개다. 800자 이상이면서 문항이 서로 다른 복수 역량을 요구할 때만 보조 경험 1개를 고려한다. 보조 경험은 주 경험에 없는 증거 한 가지만 보완하고 별도 문단으로 분리한다. 문항이 복수 사례나 목록을 요구하면 그 지시가 우선한다.

## 5. 문항별 역할 분리

문항마다 독자가 기억해야 할 메시지를 한 문장으로 정한다. 같은 경험을 여러 문항에서 사용해야 한다면 장면·역할·판단·결론을 분리한다.

예를 들어 한 경험을 가치관 문항에서는 기준이 생긴 계기로, 역량 문항에서는 실제 행동의 근거로 사용할 수 있다. 두 문항에서 같은 사건과 교훈을 반복하지 않는다.

여러 문항을 한꺼번에 쓸 때는 경험 배정표를 먼저 만들고 다음을 확인한다.

- 각 문항의 중심 메시지가 다른가
- 같은 수치와 행동을 반복해 분량을 낭비하지 않는가
- 한 문항에서 빠진 하위 요구를 다른 문항의 내용으로 대신하지 않았는가
- 자유소개가 나머지 답변의 요약문으로만 끝나지 않는가

## 6. Q–E–J–A–R–T 편집 점검

다음 구조를 누락 점검에 사용한다.

| 단계 | 확인 질문 | 써야 할 내용 |
|---|---|---|
| Q · Question fit | 이 문항에 대한 직접적인 답은 무엇인가 | 핵심 역량·선택 이유·해결 원칙 |
| E · Evidence context | 왜 이 사례가 증거가 되는가 | 문제·목표·제약·본인 역할 |
| J · Judgment | 무엇을 보고 어떻게 판단했는가 | 관찰·가설·대안 비교·선택 이유 |
| A · Action | 본인이 정확히 무엇을 했는가 | 조사·설계·구현·조정·실험·검증 |
| R · Result | 무엇이 달라졌는가 | 수치 또는 검증 가능한 비수치 증거 |
| T · Transfer | 목표 직무에서 무엇을 재사용하는가 | 실제 업무 단계·대상·성과 기준 |

Q–E–J–A–R–T는 새로운 합격 공식이나 고정 문장 순서가 아니다. 문항의 평가 의도와 글자 수에 따라 순서와 비중을 조정하고, 사실 장부가 뒷받침하지 않는 단계를 채우지 않는다.

짧은 문항에서는 상황 설명을 줄이고 판단·행동·결과를 우선한다. 긴 문항도 경험 수를 늘리기보다 판단 전환, 대안 비교, 검증 과정의 깊이를 먼저 늘린다.

## 7. 결과와 증거

결과는 숫자와 같은 말이 아니다. 다음과 같은 비수치 결과도 검증 가능한 증거가 될 수 있다.

- 실제 배포·현장 적용·운영
- 제안·설계·개선안 채택
- 후속 프로젝트나 다른 팀의 재사용
- 승인·수상·본선·품질 통과
- 고객·현직자·상급자의 구체적인 피드백
- 일정 회복, 오류 재현, 문제 원인 범위 축소
- 표준·매뉴얼·체크리스트·자동화 파이프라인·산출물 생성

수치를 쓸 때는 가능하면 `기준선 → 개입 → 변화 → 업무 의미`를 보여 준다. 기간·표본·횟수처럼 규모를 설명하는 숫자를 성과 수치처럼 포장하지 않는다. 기억이 불확실하면 정밀한 숫자를 만들지 말고 원기록에서 확인하거나 비수치 증거로 바꾼다.

시간·성능 지표는 이름과 범위를 보존한다. 전체 처리시간, 첫 응답시간, 배치당 처리시간, 결과 제공 간격, 건당 시간, 체감 대기시간을 서로 바꾸어 쓰지 않는다. 예를 들어 `약 30초마다 부분 결과를 제공`을 `전체 작업을 약 30초 만에 완료`로 축약하지 않는다.

결과가 없거나 아직 검증 전이면 학습·가설·향후 검증 계획과 성과를 구분해 쓴다. `더 좋아졌다`, `효율을 높였다`처럼 평가 기준이 없는 표현은 구체화하거나 확인 항목으로 남긴다.

## 8. 판단이 보이는 행동 서술

기술 스택보다 다음 연결을 우선한다.

`상황과 제약 → 관찰·측정 → 판단 → 방법 선택 → 실행 → 결과 → 적용 범위`

다음 질문 중 사실로 답할 수 있는 것을 고른다.

- 왜 이 문제를 먼저 풀었는가
- 사용할 수 있는 데이터와 자원은 무엇이었는가
- 원인을 어떻게 좁혔는가
- 다른 방법과 무엇을 비교했는가
- 선택한 방법이 제약에 왜 맞았는가
- 무엇으로 결과를 확인했는가
- 결과가 어느 범위에만 적용되는가

모든 경험에 실패나 대안 비교를 억지로 넣지 않는다. 실제로 가설이 틀렸거나 방법을 바꾼 경우에만 전환을 쓰며, 사후에 만든 교훈을 당시 판단처럼 바꾸지 않는다.

## 9. 기술명과 직무기술서 표현

기술명을 일괄 삭제하지 않는다.

### 이름을 유지한다

- 공고가 특정 도구나 프로그램 경험을 요구·우대한다.
- 해당 기술을 직접 사용한 사실이 직무 역량의 핵심 증거다.
- 여러 대안 중 그 기술을 고른 이유가 문제 해결의 핵심이다.
- 업계 독자에게 통용되는 정확한 용어가 일반화된 표현보다 명확하다.

### 기능 수준으로 풀어 쓴다

- 정확한 모델명·크기·버전이 판단과 결과에 영향을 주지 않는다.
- 기술 이름이 연속되어 문제·판단·행동을 가린다.
- 비전문 독자가 별도 설명 없이 의미를 이해하기 어렵다.
- 다른 도구로 바꿔도 경험의 핵심이 달라지지 않는다.

기술명을 쓸 때는 가능하면 `무엇에 사용했는지 + 왜 골랐는지 + 무엇이 달라졌는지`를 함께 밝힌다. 목록만 나열하거나 숙련도를 근거 없이 상·중·하로 표현하지 않는다.

직무기술서의 정확한 명사와 업계 용어는 지원자의 경험을 회사가 이해하는 언어로 번역할 때 사용한다. 문장이나 항목 순서를 복사하거나, 경험하지 않은 업무를 공고 용어로 새로 만들지 않는다. 실제 경험이 없다면 과거 성과가 아니라 학습·검증 계획으로 한정한다.

## 10. 회사 조사와 직무 전이

회사 소개를 많이 쓰는 것이 목적이 아니다. 지원자의 기준·동기·계획을 증명하는 사실만 고른다.

- 공식 채용공고, 회사 공식 자료, 공시 등 1차 자료를 우선한다.
- 회사의 실제 업무·제품·고객·기술환경 중 주장과 직접 연결되는 사실만 선택한다.
- 자료의 표현을 그대로 옮기지 말고 지원자의 문제의식과 준비 증거에 연결한다.
- 경쟁사 이름으로 바꿔도 그대로 성립하는 칭찬은 줄인다.
- 확인하지 않은 최신 전략·성과·내부 업무 방식을 단정하지 않는다.
- 지원자의 아이디어나 검증 전 문제 가설을 확인된 고객 사실처럼 쓰지 않는다. `가설로 보고 확인하겠다`처럼 상태를 드러낸다.

직무 전이는 `기여하겠습니다`로 끝내지 않는다. 경험에서 검증된 판단 방식·점검 절차·조사법을 목표 직무의 실제 업무 단계, 대상, 성과 기준 중 하나 이상과 연결한다.

직무 연결의 강도를 조절한다.

- 직접 수행한 경험: 확인된 범위에서 단정적으로 쓸 수 있다.
- 유사 경험: 전이 가능한 원리와 실제 직무와의 차이를 함께 밝힌다.
- 해보지 않은 업무: 가능성을 성과처럼 쓰지 말고 학습·검증 계획으로 한정한다.

## 11. 마무리 원칙

본문에서 증명하지 않은 역량을 마지막에 새로 주장하지 않는다. 추상적인 성장·교훈·포부 대신 경험에서 확인된 행동 방식, 이후 실제로 바꾼 행동, 또는 목표 직무에서의 구체적인 재사용을 남긴다.

`소통의 중요성을 배웠습니다`보다 이후 갈등 상황에서 무엇을 먼저 확인하고 어떤 기준으로 움직이는지를 쓴다. 다만 문항이 느낀 점만 요구하거나 직무 전이를 요구하지 않으면 억지로 회사 기여 문장을 붙이지 않는다.

## 12. 최종 하드게이트

초안 전에 충돌한 값, 확인되지 않은 개인 역할, 범위가 불명확한 지표를 `사용 금지 주장`으로 기록한다. 제출 직전에는 최종본과 확인 필요 목록을 함께 검사한다. 확인 필요 항목의 답에 따라 본문의 진위·주체·범위가 달라진다면 그 문장은 아직 제출 가능한 문장이 아니다. 삭제하거나 확인된 공통 표현으로 낮춘 뒤 다시 검사한다.

다음 항목을 순서대로 확인한다.

1. 원문 질문과 모든 하위 요구에 답했는가
2. 지정 형식·항목 순서·필수 키워드를 지켰는가
3. 입력창 기준 글자 수와 최소·최대 범위를 확인했는가
4. 회사·조직·직무·고용 형태가 현재 지원 대상과 일치하는가
5. 블라인드·개인정보·대외비 금지 항목을 지켰는가
6. 다른 회사명, 복사 문구, 편집 메모, 임시 표시가 남지 않았는가
7. 주체·기간·수치·성과·기술명이 원기록과 일치하는가
8. 팀 산출물만으로 개인의 직책·판단·구현·제안·전달 행위를 새로 만들지 않았는가
9. 충돌하거나 확인되지 않은 사실을 경고만 붙인 채 본문에 남기지 않았는가
10. 수치의 기준선·범위·측정 조건을 설명할 수 있는가
11. 시간·성능 수치가 전체·첫 응답·배치·간격·건당 중 원기록과 같은 지표를 가리키는가
12. 회사 사실과 최신 정보의 출처를 확인했는가
13. 지원자의 문제 가설을 확인된 고객·회사 사실처럼 단정하지 않았는가
14. 면접에서 각 행동의 이유와 결과를 사실대로 설명할 수 있는가

하드게이트가 하나라도 불확실하면 확인 항목으로 분리하고, 임의의 문장으로 빈칸을 메우지 않는다. `사용 금지 주장`이 제출용 본문에 한 건이라도 남아 있으면 최종본을 반환하지 말고 먼저 수정한다.
