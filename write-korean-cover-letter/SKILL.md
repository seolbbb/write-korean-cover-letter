# 한국어 자기소개서 작성

질문에 무엇으로 답할지 정하고, 그 답에 필요한 사실을 골라 처음 읽는 사람이 이해할 순서로 쓴다. 실제 경험에서 나온 판단과 행동으로 주장을 증명하고, 문장 사이의 논리를 검토한 뒤 문체를 다듬는다. 직무 용어와 기술명은 필요한 만큼 정확히 사용하되 나열로 대신하지 않는다.

## 적용 우선순위

사용자의 현재 요청 범위, 명시적인 수정 지시와 이미 합의한 내용은 아래의 일반적인 작성 권고보다 우선한다. 문항 조건이나 사실과 충돌하는 지시는 그 충돌을 설명하고 사실을 만들어 메우지 않는다. 작성 근거와 제출 조건은 다음 순서로 판단한다.

1. 현재 공고의 문항·평가표·제출 형식·글자 수·블라인드 지침
2. 사용자가 제공한 사실과 원기록
3. 여러 출처가 함께 지지하는 고신뢰 작성 원칙
4. 합격 사례에서 관찰된 선택적 패턴
5. 문체와 표현 선호

합격 사례의 빈도나 특정 표현을 합격 원인으로 단정하지 않는다. 상위 규칙을 지키기 위해 하위 규칙은 적용하지 않거나 조정할 수 있다.

## 참조 문서

- 작성·수정·검토 전에는 [경험과 근거 중심 작성 규칙](references/evidence-and-drafting.md)을 읽는다.
- 새로 쓰거나 문항 구조를 크게 바꿀 때는 [문항별 판단 구조](references/question-patterns.md)를 읽고 해당 문항 유형만 적용한다.
- 내용이 확정된 뒤 문체를 다듬거나 AI 문체를 검사할 때는 [한국어 문체 검토](references/style-review.md)를 읽는다.
- 기존 답변을 수정하거나 최종 제출 가능 여부를 검토할 때는 [수정 합의와 최종 검토](references/revision-and-final-review.md)를 읽는다.
- 사용자가 `humanize-korean`을 명시하면 이 Skill의 사실·구조 검증을 먼저 끝낸 뒤 해당 Skill을 별도로 읽고 따른다.

## 작업 순서

### 1. 제출 하드게이트를 확정한다

공고와 사용자가 제공한 자료에서 다음을 먼저 기록한다.

- 원문 문항과 모든 하위 질문
- 지정된 항목 순서·목록·키워드·소제목 등 제출 형식
- 최소·최대 글자 수와 계산 기준
- 회사·조직·직무명, 필수·선택 여부, 마감
- 블라인드 및 기재 금지 항목
- 작성, 부분 수정, 검토, 소재 선정 중 요청 범위

현재 자료와 대화에서 확인할 수 없는 중요한 내용만 사용자에게 묻는다. 검토만 요청받았다면 임의로 파일이나 제출본을 수정하지 않는다. 이미 합의한 문단, 제외한 소재, 수정할 범위를 현재 대화에서 확인해 유지한다.

### 2. 사실 장부를 만든다

제공된 자료를 먼저 읽고 상황·제약, 본인의 판단과 행동, 타인의 행동, 팀 결과, 수치와 적용 범위, 확인 상태를 분리한다. 팀 산출물이 존재한다는 사실과 지원자가 직접 판단·구현·전달했다는 사실을 별도로 검증한다. 기록이 충돌하면 확인을 요청하거나 충돌하는 표현을 빼고, 임의로 하나를 고르지 않는다. 확인 필요 목록에 적었다는 이유로 충돌한 값을 제출용 본문에 남기지 않는다. 자세한 기준은 `references/evidence-and-drafting.md`를 따른다.

### 3. 필요한 조사만 한다

- 현재 회사·공고·산업 정보가 필요하면 최신 자료를 확인한다.
- 회사 적합성은 공식 채용공고, 회사 공식 자료, 공시 등 1차 자료를 우선한다.
- 합격 자기소개서는 구조와 설명 밀도를 관찰하는 용도로만 사용하고 문장이나 경험을 모방하지 않는다.
- 회사 자료를 나열하지 말고 지원자의 기준이나 목표를 증명하는 사실만 고른다.

### 4. 문항별 메시지와 경험을 배정한다

각 문항에 무엇으로 답할지 정하고, 문단별로 주장·배경·판단과 행동·결과·목표 중 어떤 역할을 맡길지 정한다. 이 구분은 편집용이며 제출문에 붙이는 소제목이나 고정 순서가 아니다. 후보 경험은 문항 적합성, 본인의 판단, 필요한 설명량을 먼저 보고 직무 과업과의 관련성을 비교한다.

정보의 중요도에 따라 분량을 배분한다. 경험 수나 글자 수에 따른 고정 공식을 두지 않는다. 같은 강점을 다른 제약에서 증명하는 복수 경험도 사용할 수 있지만, 이름과 성과만 나열할 정도로 얕아지면 핵심 사례를 남긴다. 약점·가치관에서는 반복된 실천을 보여주는 일상 경험도 사용할 수 있다.

직무역량 문항에서는 `해야 하는 일`과 `그 일을 수행할 능력`을 구분한다. 직무 설명에 `역량`이라는 단어만 붙이지 말고, 무엇을 이해·분석·판단·설계·검증할 수 있어야 하는지 정의한다. 경험은 그 능력을 보여줘야 하며, 관련 기술을 썼다는 이유로 경험하지 않은 업무까지 수행했다고 확대하지 않는다.

같은 경험을 여러 문항에서 써야 한다면 역할·장면·판단·결론을 분리한다. 여러 경험을 비교했다면 선정·제외 이유를 사용자에게 별도로 설명하고 제출용 본문에는 넣지 않는다.

### 5. Q–E–J–A–R–T로 누락을 점검한다

다음 항목을 고정 문장 틀이 아니라 편집 체크리스트로 사용한다.

- Q · Question fit: 문항에 대한 직접적인 답
- E · Evidence context: 문제·목표·제약·본인 역할
- J · Judgment: 관찰·가설·대안 비교·선택 이유
- A · Action: 본인이 실제로 한 구체 행동
- R · Result: 수치 또는 검증 가능한 비수치 증거
- T · Transfer: 검증된 방식을 목표 직무의 실제 단계에서 재사용하는 방법

문항과 글자 수에 필요하지 않은 단계는 억지로 늘리지 않는다. 사실 장부가 뒷받침하지 않는 판단·실패·결과·직무 연결을 새로 만들지 않는다.

프로젝트 이름이나 기술명 전에 어떤 환경에서 무엇을 만들었고 무엇이 문제였는지 이해할 최소 배경을 준다. 도입을 길게 늘리거나 모든 문항에 경력 소개를 삽입하지 않는다. 지원동기는 실제 관심과 선택 이유, 꿈은 원하는 사용자 경험이나 결과로 답할 수 있으며, 요구하지 않은 준비 경험·학습 계획·기여 다짐으로 채우지 않는다.

### 6. 내용 검증을 끝낸다

문체를 다듬기 전에 사실 장부에서 충돌한 값과 근거 없는 개인 역할을 `사용 금지 주장`으로 모은다. 최종본과 확인 필요 목록을 대조하고, 확인 결과에 따라 진위·주체·범위가 달라질 주장이 본문에 있으면 반환 전에 삭제하거나 확인된 공통 표현으로 낮춘다. 확인 필요 목록만 덧붙인 채 불확실한 제출 문장을 유지하지 않는다.

그다음 다음을 확인한다.

- 원문 질문과 모든 하위 질문에 답했는가
- 지정 형식·글자 수·블라인드 기준을 지켰는가
- 주체와 기여 범위가 정확한가
- 팀 산출물만으로 개인의 역할·직책·제안 대상·전달 행위를 새로 만들지 않았는가
- 확인되지 않았거나 자료끼리 충돌한 사실·수치·명칭이 본문에 남아 있지 않은가
- 모든 수치의 기준선·범위·측정 조건을 설명할 수 있고, 배치 간격·첫 응답·전체 처리처럼 서로 다른 지표를 바꾸어 쓰지 않았는가
- 수치가 없다면 채택·배포·재사용·피드백·산출물 같은 증거가 있는가
- 선택 이유와 제약이 사실에 근거해 보이는가
- 직무 설명과 필요한 역량, 그 역량을 보여주는 경험이 구분되는가
- 앞 문장이 뒤 문장의 근거인지, 예시가 상위 주장을 보여주는지, 병렬 사례를 억지 순서로 묶지 않았는지 확인했는가
- 문항별 중심 메시지가 불필요하게 겹치지 않는가
- 회사 사실과 직무 연결이 실제 과업을 뒷받침하는가
- 면접에서 각 주장과 행동을 방어할 수 있는가

### 7. 마지막에 문체를 다듬는다

내용을 확정한 뒤 `references/style-review.md`의 순서로 검사한다. 문체를 고치면서 새로운 사실·성과·수치·교훈을 추가하지 않는다. 접속사는 실제 관계를 드러낼 때 사용하고, 단어 금지 목록으로 자연스러움을 판단하지 않는다. 수정한 문장뿐 아니라 앞뒤 문장과 해당 문단을 다시 읽는다.

최종 검토는 최신 실제 제출본을 기준으로 문항 간 중복·충돌과 사실·논리·문법·분량을 함께 확인한다. `제출 전 수정 필요 / 선택적인 개선 / 현재 글의 한계`를 구분해 발견한 문제를 한 번에 모아 제시한다. 새 문제를 발견하면 고치되, 새 근거 없이 취향에 따른 수정을 필수로 바꾸어 제출 판단을 계속 미루지 않는다.

## 출력

사용자가 요청한 범위에 맞춰 다음 중 필요한 것만 제공한다.

- 제출용 최종 답변과 문항별 글자 수
- 수정 이유와 대안 문장
- 사용 가능한 경험 목록과 선정·제외 이유
- 확인이 필요한 사실과 수치
- 회사 조사 근거

최종본과 사용자용 판단 문서를 분리한다. 사용자가 파일을 요청하지 않았다면 임의로 문서를 만들지 않는다.
